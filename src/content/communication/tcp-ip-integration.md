# TCP/IP 通讯：客户端、服务端与断线重连

TCP 是读码器与上位机最常见的通讯方式。稳定运行的关键不是“能连上”，而是断线后能自动恢复、报文不会混。

## 一、先确认角色

| 模式 | 读码器角色 | 谁发起连接 |
| --- | --- | --- |
| 读码器作服务端 | Server | 上位机 |
| 读码器作客户端 | Client | 读码器 |
| 双向 | 视配置 | 取决于工程 |

多数产线用“读码器作服务端、上位机作客户端”，因为上位机更容易统一管理连接。

## 二、报文设计

建议明确：

- 触发命令（如 `start`）
- 结果格式（码内容、状态、时间戳）
- 分隔符
- 结束符（换行或固定长度）
- 失败时的返回值
- 多码时的顺序

```text
OK,CODE123456,2026-10-26T10:12:33
NG,,2026-10-26T10:12:34
```

## 三、连接管理

生产代码至少要有：

- 连接超时
- 读超时
- 心跳或空闲检测
- 断线重连
- 重连退避
- 连接状态日志

不要每次触发都新建连接。频繁建连会增加延迟和不稳定。

## 四、粘包与拆包

TCP 不保证“一次 recv 就是一条完整消息”。要按结束符或固定长度解析：

```python
buffer = b""
while True:
    chunk = sock.recv(4096)
    buffer += chunk
    while b"\n" in buffer:
        line, buffer = buffer.split(b"\n", 1)
        handle(line.decode())
```

## 五、上线检查

- [ ] IP 与端口固定，不依赖 DHCP
- [ ] 防火墙放行
- [ ] 断线自动重连
- [ ] 超时与重试上限
- [ ] 报文编码一致（UTF-8）
- [ ] 多工位隔离
- [ ] 日志可追溯

## 六、常见问题

- **连上但无结果**：触发命令不匹配、未保存触发模式。
- **偶发超时**：网络抖动、读码器忙、上位机发送过快。
- **重启后 IP 变了**：DHCP 租约变化，改为固定 IP。
- **多台设备串数据**：端口或工位号未隔离。
